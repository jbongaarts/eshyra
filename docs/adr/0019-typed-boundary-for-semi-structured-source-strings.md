# ADR 0019: Typed boundary for semi-structured source strings

Status: Accepted  
Date: 2026-07-14  
Bead: `eshyra-o9bd.18.8.8`

## Context

The importer intentionally preserves a large amount of SRD wording. Some of
that wording is evidence or narration; some is a closed scalar; some is a
compound mechanical clause. Treating all strings alike creates two failures:
deterministic code either reparses authoritative prose ad hoc, or a generic
“parsed string” layer claims semantics that the importer did not establish.

This decision follows the 2026-07 audit/classification material, especially the
rules-pack compiler procedure in `docs/rules-pack-compiler.md`, the 18.7.8
rule/execution classifications, and the 18.7.9 engine-domain audits. It applies
to future importer and engine work; it does not rewrite the frozen SRD pack.

## Decision

Typing is driven by deterministic authority, not syntax. A field needs a typed
projection when deterministic code must calculate from it, enforce it, compare
or filter by it, resolve a reference from it, validate another declaration
against it, audit mechanical completeness/parity, expose it as a closed player
or tool choice, or replay its effect without model interpretation. Commas,
numbers, parentheses, and recognizable patterns are not sufficient reasons.

The source wording remains canonical evidence. A projection is an explicit,
domain-named view of that evidence. A record body or named entry is sufficient
source retention when it contains the complete clause unambiguously; a local
`text` field is needed when the projection would otherwise detach or truncate
the clause. Do not add duplicate raw fields when the existing body/entry is
already unambiguous.

There is no universal `{ raw, parsed }`, `{ value, tokens }`, or
`Record<string, unknown>` parsed-string contract. A domain that cannot name its
semantics retains prose until its deterministic owner and closed contract
exist. Shared types describe shared semantics, not coincident English labels
such as `speed`, `range`, or `proficiency`.

### Disposition vocabulary

Every inventoried candidate has exactly one of these dispositions:

| Disposition | Meaning and required behavior |
| --- | --- |
| `complete` | A closed projection represents every mechanically relevant clause. The schema and deterministic consumer are named. Recognized grammar emits it; drift fails the importer/readiness gate. |
| `typed-core-with-prose-qualifier` | A closed core is exact and independently usable; a specifically identified remainder is retained as prose and explicitly requires adjudication. Consumers use only the core. |
| `model-adjudicated` | The complete clause remains source text because no deterministic consumer owns it; model interpretation is the intended terminal boundary over available tools. |
| `unsupported` | Deterministic execution needs structure that is not implemented. Source is retained, the owner/reason is named, and readiness must not claim deterministic support. |
| `not-mechanical` | Display, flavor, naming, or provenance/source evidence only. |

`model-adjudicated` is not a parser failure. `unsupported` is not an invitation
to invent a parser. A field may move from model-adjudicated to typed only when
the bead owning the deterministic consumer establishes the domain contract.

### Decision matrix

| Deterministic consumer? | Grammar closed? | Complete representation possible? | Disposition |
| --- | --- | --- | --- |
| No | irrelevant | irrelevant | `model-adjudicated` or `not-mechanical` |
| Yes | No | No | `unsupported`; retain source |
| Yes | Yes | Yes | `complete` typed projection |
| Yes | Partially | Typed core independently valid | `typed-core-with-prose-qualifier` |

Parsers fail closed inside their declared authority. A `complete` parser emits
the projection or fails on source drift/unsupported grammar; it never silently
omits a clause. A partial parser marks the qualifier and retains it. The other
three dispositions retain source and do not imply deterministic gameplay
support.

## Core versus system-specific ownership

The shared rules model owns references, provenance, record identity, and other
semantics demonstrably common to systems. D&D movement modes, its monster
stat-block conventions, and its weapon-property grammar remain D&D projections.
Pathfinder action costs, traits, traditions, bulk, and proficiency ranks remain
Pathfinder data and validators. The seven-record Pathfinder fixture is evidence
of this boundary, not a proposal for a universal parser. Similar field names do
not establish shared semantics.

## Current repository inventory

The reproducible inventory is generated by
`packages/core/scripts/inventory-semi-structured-boundary.ts` and committed as:

- [`o9bd-18-8-8-semi-structured-boundary.json`](../inventories/o9bd-18-8-8-semi-structured-boundary.json), the machine-readable artifact;
- [`o9bd-18-8-8-semi-structured-boundary.md`](../inventories/o9bd-18-8-8-semi-structured-boundary.md), the review table.

It scans all string scalars and string arrays in every active D&D record kind
and record metadata, plus every field in the representative Pathfinder fixture.
It groups repeated wildcard paths within each record kind and records kinds, representative values,
population, current kind-schema validation, consumers, audit/readiness
assumptions, disposition, owner, and future-work status. It reads pack data and
writes only the two documentation artifacts.

The one-disposition-per-candidate convention is field-level bookkeeping, not
exclusive clause, procedure, discovery, or capability ownership. A record may
have both a typed projection and an untyped residual for the same concept (for
example, `equipment:battleaxe` retains a source `data.properties` value beside
its typed `weaponProperties[]`). Discovery may use the census only for
exploratory candidate generation and projection-limit disclosure; it must not
use it as an ownership claim. ADR-level follow-up review remains this ADR's
own successor.

The 2026-07-14 baseline contains 1,813 D&D records across 16 active kinds and
7 Pathfinder records, yielding 1,196 grouped string paths after metadata is
included. The generated disposition census is the authority; the current
baseline is 257 `complete`, 2 `typed-core-with-prose-qualifier`, 739
`model-adjudicated`, 192 `not-mechanical`, and 6 `unsupported` rows. Run
`npx tsx packages/core/scripts/inventory-semi-structured-boundary.ts --check`
to verify the committed output is current.

The five explicit residual families are `creature.data.savingThrows`,
`creature.data.skills`, and `creature/stat-block.data.senses` (owner
`eshyra-o9bd.18.7.9.15`), `equipment.data.properties[]`
(`eshyra-o9bd.18.7.6`), and `magic-item.data.attunementRequirement`
(`eshyra-o9bd.18.7.7.1` / `.7.7`). These remain strings in the frozen pack and
are not silently treated as executable. No new bead is created: these owners
already exist.

## Concrete classifications

The following are representative decisions; the generated inventory is the
complete field-level census.

* Spell `castingTime`, `range`, `components`, and `duration` remain canonical
  source strings/closed arrays at the record boundary. Existing
  `spell.mechanics.duration` is a domain-specific typed projection where the
  importer has established the duration semantics. The raw duration remains
  necessary evidence, particularly for concentration qualifiers. Metadata such
  as range does not become typed merely because it says `30 feet`; it becomes a
  projection when a range/targeting consumer owns that contract.
* Creature `speed` is already structured by movement mode. Creature
  `savingThrows`, `skills`, and `senses` are semi-structured residuals and are
  `unsupported` for future deterministic consumers, not a license for callers
  to split commas. Defenses, saves, skills, challenge metadata, and sense
  projections already present under `mechanics` are typed-core projections only
  where their domain contract is explicit.
* Class proficiencies, proficiency choices, equipment grants, and progression
  values are typed when used by character creation/progression. The original
  class `startingEquipment.text` remains prose evidence; the structured
  `startingEquipment` projection is the consumer-owned contract. Choice
  `from`, option ids, primary abilities, spell-preparation fields, language
  grant domains, and references are closed choice/reference data, not generic
  parsed strings. These are complete projections because
  `rulesPackResolver.ts`, `srdCreationChoices.ts`, and the progression table
  consumers read them deterministically.
* Equipment damage, cost, weight, armor fields, and grouping have named fields
  and existing equipment filters. `properties[]`, including `Ammunition (range
  150/600)` and `Versatile (1d10)`, is the notable unsupported residual owned by
  the equipment domain. It must become a closed equipment-property projection
  or stay prose as that bead decides; no universal property parser is allowed.
* Magic-item rarity, type/category, attunement, charges, activation, and prose
  effects are separate concerns. Existing passive mechanics are typed domain
  projections; charge economy/activation/attunement qualifiers remain
  unsupported or prose under their existing state-contract beads. The complete
  item body is sufficient raw evidence, so duplication is not required.
* Feature prerequisites, choices, formulas, and advancement triggers are typed
  when the choice/progression resolver consumes them. A prerequisite sentence
  or trigger qualifier without a closed owner remains prose or
  `typed-core-with-prose-qualifier` with its retained entry text.
* Table cells are source strings by default. `tableRefs` and table-derived
  semantic projections are typed when lookup, parity, or character progression
  consumes them. A number-looking cell is not itself a typed formula.
* Rule-record `data.text`, action/trait text, and descriptions are canonical
  source/display evidence. `record.provenance.sourceRef` is different: it is a
  complete source-corpus identity validated by
  `assertProvenanceMatchesPackSource`; `locator` and `note` remain provenance
  evidence. Rule classifications and source-coverage audits may classify prose
  content, but that does not make it a deterministic projection.

## Compatibility and schema evolution

This ADR adds no record fields and changes no validator, generated record,
manifest, readiness count, or freeze hash. Existing consumers remain compatible.
Future projections should be additive and domain-named; a projection must not
replace source wording. A bead that owns a deterministic consumer owns its
projection, validator, parser/readiness gate, audit evidence, and migration
decision. Do not create a parallel follow-up bead when an existing owner listed
in the inventory already covers the work.

Future prompts and code reviews must name: the deterministic authority; the
closed grammar and failure behavior; the complete versus qualifier boundary;
the retained source field/body; the system owner; the audit/readiness gate; and
the existing bead. Reviewers should reject silent optional typing, generic
raw/parsed wrappers, ad-hoc consumer parsing, and readiness claims unsupported
by a typed consumer.

## Non-goals

This decision does not convert residual strings, implement magic-item,
consumable, rest, upcast, or Pathfinder work, rewrite schemas broadly, alter
readiness classifications, or modify frozen D&D/PF data. It does not require a
shared parser for fields that merely share an English label. It does not make
the model adjudication disposition a claim that a clause is mechanically
implemented.
